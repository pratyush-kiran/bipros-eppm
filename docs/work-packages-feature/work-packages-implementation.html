Work Packages page

A new project sub-page that rolls activity-level data up into per-work-package metrics — counts, weighted progress, days behind, EVM (SPI/CPI/SV/CV), and critical-path indicators — computed on-the-fly with no persisted recompute.

Branch: hemendra-pilot-e2e-and-rbac-fixes Endpoint: GET /v1/projects/{projectId}/work-packages Page: /projects/[projectId]/work-packages

What changed

The repo already had a slim Work Package Status card embedded in the project dashboard (10 activities, 6 columns). It was actually a top-10 activity list keyed by WBS code — not a true work-package surface. This change builds the missing dedicated page on a backend aggregator that joins WBS, Activity, and EVM into one flat row per leaf work package.

Derivation rules (kept honest, kept testable)

Weighted % complete

SUM(originalDuration × percentComplete) / SUM(originalDuration) across all activities under a WBS. If the denominator is 0 (no durations set), falls back to a plain average. If there are no activities at all, the WBS's own seeded summaryPercentComplete is returned.

Days behind schedule (3-branch)

  1. Complete → 0 (the work is done).
  2. Past planned finish and incomplete → calendar days late (today − derivedPlannedFinish).
  3. In flight → planned %-elapsed minus actual %-complete, scaled by duration: (plannedPct − actualPct) / 100 × duration. Negative gap (ahead) clamps to 0.

Returns null when neither activity nor WBS dates exist.

Status (first match wins)

RuleResult
weighted % ≥ 100DONE
0 activities under the WBSPLANNED
today > planned finish and not completeDELAYED
SPI < 0.9AT_RISK
daysBehind > 10 % of durationAT_RISK
0 % complete and today < planned startNOT_STARTED
otherwiseIN_PROGRESS

Min total float / critical path

The lowest Activity.totalFloat across activities under a WBS. onCriticalPath is true when that minimum is ≤ 0 — meaning at least one activity on the work package has no slack.

Architecture choice — why bipros-api

The project's CLAUDE.md is explicit: domain modules can't depend on each other. This endpoint reads from bipros-project (WBS), bipros-activity (Activity), bipros-evm (EVM rollup), and bipros-admin (Organisation) — so the only legal home is the aggregator module bipros-api, which depends on all of them. The pattern follows existing aggregators like EvmKpiController, ContractorPerformanceController, and ManpowerKpiController.

Trade-off accepted: Rollup is computed on every request, not persisted. For typical projects (≤ 1k activities) this is a few hundred milliseconds of in-memory math after three repository reads. If perf becomes an issue, switch EvmRollupService.calculateWbsTree for the cached EvmCalculationRepository.findTopByProjectIdAndWbsNodeId — the rest of the service stays the same.

What's intentionally out of scope

  • Persisting recomputed rollups back to WbsNode.summaryPercentComplete. The seeded placeholder columns are untouched.
  • EVM technique / ETC-method selector on this page. We pin ACTIVITY_PERCENT_COMPLETE + CPI_BASED to match the standalone EVM page's defaults.
  • Inline edit of work-package fields. That stays on the WBS detail drawer.
  • Excel export — the button is wired but disabled with a tooltip.
