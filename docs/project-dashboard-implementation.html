4 · KPI row — the four tiles

Reuses KpiTile (5 tonal variants, top stripe, optional delta pill). Layout: grid-cols-1 sm:grid-cols-2 xl:grid-cols-4.

Tile Value formula Tone Source
Overall Progress snapshot.physicalPct.toFixed(0) + "%" success /status-snapshot-with-trend
Budget Utilised "₹" + snapshot.bacCrores.toFixed(1) + " Cr" accent /status-snapshot-with-trend
Tasks Completed tasks.done with hint "of {tasks.total} total" default derived from /activity-status
Open Issues count of severity === "CRITICAL" & status in {OPEN, IN_PROGRESS} danger /dpr-issues

Tasks-completed derivation

// dashboardDerivations.ts → tasksCompleted(rows)
const done = rows.filter(r =>
  r.pctComplete >= 100 ||
  r.status === "DONE"  ||
  r.status === "COMPLETED"
).length;
const total = rows.length;
// {done: 30, total: 209}  →  "30  of 209 total"

Critical-issue count

// dashboardDerivations.ts → criticalIssueCount(issues)
const ACTIVE = new Set(["OPEN", "IN_PROGRESS"]);
issues.filter(i => i.severity === "CRITICAL" && ACTIVE.has(i.status)).length

Delta pills (the optional secondary number on every tile)

Today the backend stub returns null for every delta. The frontend treats null as "render no pill" so the tile shows just the headline number with no layout shift. When the snapshot-history writer lands, the same UI will start showing +/− pills automatically — no frontend change needed. 
// dashboardDerivations.ts → formatDelta(curr, delta, opts)
//   opts.unit, opts.digits, opts.invertColor
// returns undefined when curr or delta is null  →  KpiTile renders no pill
//
// |delta| < 10^-digits/2  →  { value: "0.0", direction: "flat" }
// delta > 0                →  { value: "+1.2", direction: invertColor ? "down" : "up" }
// delta < 0                →  { value: "-1.2", direction: invertColor ? "up"   : "down" }
//
// invertColor=true is used for "more is worse" metrics — Budget Utilised and
// Open Issues — so a rise renders red instead of green.

5 · Project Timeline Preview

Lightweight SVG-free Gantt strip rendered with absolutely-positioned divs and percentage widths — deliberately separate from the heavy GanttChart on the schedule page.

Window

const today        = new Date();
const windowStart  = startOfMonth(addMonths(today, -1));   // last month
const windowEnd    = addMonths(windowStart, windowMonths); // default 6
const totalDays    = differenceInDays(windowEnd, windowStart);

So the visible band always starts on the first of last month and runs forward 6 months — never empty just because the project's data sits a few weeks in the past.

Row selection

  1. Input: ActivityStatusRow[] from /activity-status?limit=200.
  2. Filter to rows that have both plannedStart and plannedFinish.
  3. Take the first maxRows (default 6) — the API already returns them ordered by code.

Bar geometry (per row)

const startOffset  = max(0,        differenceInDays(start,  windowStart));
const finishOffset = min(totalDays, differenceInDays(finish, windowStart));
const widthDays    = max(1, finishOffset - startOffset);
const leftPct      = startOffset / totalDays * 100;
const widthPct     = widthDays    / totalDays * 100;

Bar colour by activity status

Bucketing (the hard part)

The backend does not ship a per-activity health enum — only status, pctComplete, isCritical, daysDelay, daysRemaining. The frontend derives the three buckets here:

// dashboardDerivations.ts → bucketActivityHealth(r)
if (r.daysDelay > 7)                          return "delayed";
if (r.daysDelay >= 1)                         return "atRisk";
if (r.isCritical && r.daysDelay >= 0 &&
    r.pctComplete < 100)                       return "atRisk";   // critical-path slack
return "onTrack";

Then the donut sums them across every activity returned by /activity-status?limit=200:

BucketLegend labelColour
onTrackOn Trackemerald
atRiskAt Riskamber
delayedDelayedburgundy

If all three are zero the donut renders "No activity data yet" instead of a hollow ring.

Where daysDelay comes from (backend side)

// ProjectInsightsController.getActivityStatus()
LocalDate today = LocalDate.now();
if (plannedFinish != null && pct < 100 && today.isAfter(plannedFinish)) {
  daysDelay = ChronoUnit.DAYS.between(plannedFinish, today);
} else if (plannedFinish != null && actualFinish != null
        && actualFinish.isAfter(plannedFinish)) {
  daysDelay = ChronoUnit.DAYS.between(plannedFinish, actualFinish);
}

Wraps the shared TanStack-backed SimpleTable with six columns.

Duerow.plannedFinishdate-fns "d MMM" or em-dash

Sort + slice

  1. Sort rows by plannedFinish ascending (nulls last, then fall back to code).
  2. Slice the first maxRows (default 10).
  3. Map each row to the column-friendly WorkPackageRow shape.

Status mapping

// dashboardDerivations.ts → mapWorkPackageStatus(r)
if (r.pctComplete >= 100)  return "COMPLETED";
if (r.daysDelay > 7)        return "DELAYED";
if (r.pctComplete > 0)      return "IN_PROGRESS";
return r.status || "NOT_STARTED";

The badge's colour comes from StatusBadge's status-to-class map (COMPLETED → success ring, DELAYED → danger ring, etc.).

Contractor column is intentionally a placeholder. Adding a real contractor requires either an N+1 call to activitySubContractorApi.listForActivity per row, or a new project-wide sub-contractor join endpoint. That endpoint is on the follow-up list — see section 12.

8 · Active Alerts panel

Pulls every DPR issue and renders the top five most-severe still-active ones.

Filter & sort

issues
  .filter(i => i.status === "OPEN"
            || i.status === "IN_PROGRESS"
            || i.status === "BLOCKED")
  .sort(severityRank)        // CRITICAL → HIGH → MEDIUM → LOW
  .slice(0, maxRows)         // default 5

The empty result renders an "All clear" block — RESOLVED / CLOSED / CANCELLED issues never appear here.

Row anatomy

  • Colored severity dot — bg-burgundy (CRITICAL), bg-amber-flame (HIGH), bg-amber-flame/70 (MEDIUM), bg-steel (LOW)
  • <StatusBadge status="CRITICAL" variant="compact" /> (reuses the same component as the table)
  • activityName uppercase mini-label when present
  • title truncated to one line

10 · Data-fetching strategy

Why client-side TanStack Query and not a server component

The parent page.tsx is already a "use client" component (useSearchParams, useRouter, optimistic mutations). Splitting one widget off as a server component would require a parallel async boundary just for that tab; we'd lose the in-place tab switching the page relies on. So every dashboard query lives in a useQuery hook inside ProjectDashboardTab.

const STALE = 60_000;  // 1 minute

useQuery({ queryKey: ["project-dashboard-snapshot-trend",  projectId], queryFn: () => projectInsightsApi.getStatusSnapshotWithTrend(projectId), staleTime: STALE });
useQuery({ queryKey: ["project-dashboard-activity-status", projectId], queryFn: () => projectInsightsApi.getActivityStatus(projectId, { limit: 200 }), staleTime: STALE });
useQuery({ queryKey: ["project-dashboard-issues",          projectId], queryFn: () => dprIssueApi.list(projectId).then(r => r.data ?? []), staleTime: STALE });
useQuery({ queryKey: ["project-dashboard-weather",         projectId], queryFn: () => dailyWeatherApi.list(projectId).then(r => r.data ?? []), staleTime: STALE });

The activity-status response feeds three independent widgets (donut, work-package table, tasks-completed KPI) — only one fetch even though three sections consume it.

11 · Backend endpoint reference

New: GET /v1/projects/{id}/status-snapshot-with-trend

Wraps the existing snapshot DTO with a nullable deltas record so the frontend can render trend pills the moment the history table lands.

// ProjectInsightsController.java
@GetMapping("/status-snapshot-with-trend")
public ApiResponse<ProjectStatusSnapshotWithTrendDto> getStatusSnapshotWithTrend(
    @PathVariable UUID projectId) {
  ProjectStatusSnapshotDto current = getStatusSnapshot(projectId).data();
  // TODO(snapshot-history): diff against project.daily_status_snapshots row from 7 days ago
  // once the JobRunr daily writer + table land. Until then deltas stay null.
  var deltas = new ProjectStatusSnapshotWithTrendDto.SnapshotDeltas(null, null, null, null);
  return ApiResponse.ok(new ProjectStatusSnapshotWithTrendDto(current, deltas));
}

Shape

ProjectStatusSnapshotWithTrendDto = {
  current: ProjectStatusSnapshotDto,
  deltas: {
    physicalPctDelta:    Double  | null,
    bacCroresDelta:      BigDecimal | null,
    activeRisksDelta:    Long    | null,
    tasksCompletedDelta: Long    | null
  }
}

12 · Open follow-ups

Backend

  • Snapshot history table. project.daily_status_snapshots with a nightly JobRunr writer; the controller stub will then read "7 days ago" and fill the deltas record. Once that lands the dashboard automatically grows the +/− pills on every tile — no frontend work.
  • Project-wide sub-contractor join. A GET /v1/projects/{id}/sub-contractor-assignments that returns one row per activity with the contractor name would let the Work Package table show real contractor strings instead of "—".
  • AQI feed. No domain endpoint exists. Until one lands the panel keeps showing "—" and the caption "Not available".

Frontend

  • Timeline preview hard-codes 6 months and 6 rows. Both are props (windowMonths, maxRows) — trivial to expose as user controls later.
  • Work-package row count is also a prop (maxRows = 10); pagination would slot in cleanly because SimpleTable already supports it.
  • Health-bucket thresholds (1 d / 7 d) live as numeric literals inside bucketActivityHealth. If the business decides to widen "At Risk" to 14 d or read off totalFloat instead of daysDelay, it is a one-line change in dashboardDerivations.ts.
